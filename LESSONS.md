# Lessons Learned

## Frontend

| # | Lesson | Sumber |
|---|--------|--------|
| 1 | **Entry point React wajib me-render root** — TypeScript/Vite dapat tetap typecheck dan build walau file hanya mendefinisikan `App`. Pastikan setiap `main.tsx` memanggil `createRoot(document.getElementById("root")!).render(<App />)` dan verifikasi bundle memuat string UI, bukan hanya React runtime. | debug |

## Supabase

| # | Lesson | Sumber |
|---|--------|--------|
| 2 | **Bedakan cloud project dan custom self-hosted URL** — `supabase db query --linked` menargetkan project cloud, sedangkan aplikasi memakai `supabase.yumme.id`. Selalu smoke-test kedua endpoint dan apply migration/deploy function ke runtime yang benar. | deployment |
| 3 | **Extension PostgreSQL dapat berada di schema `extensions`** — gunakan `extensions.digest(...)`, bukan `digest(...)`, pada function SECURITY DEFINER agar tidak bergantung pada `search_path`. | debug |
| 4 | **Payment booking harus payment-first** — simpan booking sebagai `pending` dengan hold kapasitas singkat, buat invoice Mayar lewat Edge Function, korelasikan `extraData.bookingId`, dan ubah menjadi `confirmed/paid` hanya setelah webhook memverifikasi `GET /transactions/{id}` berstatus `paid`. Redirect browser bukan bukti settlement. | payment |
| 5 | **Booking yang sudah terhubung ke finance tidak boleh di-hard-delete** — aksi hapus harus mengecek `financial_transactions`; jika ada linkage, ubah booking menjadi `cancelled` dan simpan `cancelled_at`. Physical delete hanya boleh untuk booking tanpa transaksi finansial. | safety |
| 6 | **Mini App closing wajib diverifikasi ulang di server** — jangan hanya percaya state frontend atau link verifier; `process-closing` harus memvalidasi HMAC UID/timestamp, active check-in, dan menolak duplicate checkout sebelum opname/inventory write. Settings jadwal yang gagal dibaca tidak boleh menjadi bypass validasi jam. | security |
| 7 | **Build sukses tidak berarti production sudah berubah** — untuk SPA/PWA, verifikasi `index.html`, hashed bundle, `sw.js`, dan `version.json` dari domain canonical setelah deploy. HTTP 200 pada route dapat tetap menyajikan build lama. | deployment |
| 8 | **Self-host PostgreSQL tidak selalu menyediakan helper JSONB yang diasumsikan** — RPC harus diuji pada engine production; gunakan operasi JSONB portable seperti `v_updates <> '{}'::jsonb` dan transactional rollback test sebelum rollout. | debug |
| 9 | **Setiap app Vite wajib punya publishable Supabase key saat build** — fallback URL saja tidak cukup; `import.meta.env` dibekukan saat build sehingga app tanpa `VITE_SUPABASE_PUBLISHABLE_KEY` masuk state “Supabase belum dikonfigurasi”. Simpan key production di env ignored dan sediakan `.env.example`. | deployment |

## Backend

| # | Lesson | Sumber |
|---|--------|--------|
| 10 | **Auth custom Yumi menyimpan role lewat `role_source_id`** — jangan mengasumsikan `yumi_users.role_name`; resolve nama role melalui `yumi_roles` di server-side Edge Function. | debug |
| 11 | **Notification dedupe harus server-side** — frontend polling/retry dapat memanggil sync berulang; gunakan `dedupe_key` UNIQUE dan `ON CONFLICT DO NOTHING`, lalu tambahkan guard audio di client. | notification |
| 12 | **Brand fallback harus mengikuti nama canonical terbaru** — hardcoded fallback di banyak app dapat mengalahkan konfigurasi database dan membuat nama brand lama muncul lintas UI/PWA/PDF; perubahan brand harus mencakup copy, manifest, cache identifier, dan deployment artifact. | branding |
| 13 | **Bulk selection kategori harus memakai parentId tree** — memilih kategori parent harus mencakup semua descendant categoryId, sedangkan pilihan subkategori harus tetap dapat dibatalkan sendiri; pertahankan payload `featuredProductIds[]` agar tidak perlu migration. | ui-ux |
| 14 | **Notification action payload wajib diverifikasi terhadap schema runtime sebelum deploy** — field order detail seperti `tableNumber`, `items`, dan `paymentMethod` harus diuji melalui Edge Function list setelah insert; jangan menganggap build TypeScript saja cukup untuk membuktikan kontrak JSONB/REST production. | notification |
| 15 | **POS notification sync harus memfilter order di layer aplikasi bila runtime REST memakai view camelCase** — filter PostgREST `source/createdAt` dapat menghasilkan batch kosong di internal Kong walau row live ada; ambil bounded batch terbaru, filter `createdAt` dan `source` setelah decode, lalu gunakan dedupe key idempotent. | notification/debug |
| 16 | **CSS Grid dapat membuat kartu kategori pendek ikut setinggi kartu terpanjang** — gunakan `items-start` pada grid dan `h-fit` pada card agar kategori tanpa subkategori tidak menyisakan ruang kosong besar. | ui-ux |
| 17 | **POS `/menu` tidak boleh public jika notifikasi memakai session token** — shift/order read dari Supabase public dapat membuat layar terlihat aktif walau `YumiAuthContext` kosong; route kasir harus memaksa autentikasi agar notification API memakai session yang sama. | notification/security |
| 18 | **Booking mobile harus mengikuti urutan tanggal → ringkasan tanggal → tamu + jam kedatangan** — menaruh stepper tamu sebelum kalender dan input jam jauh di bawah kalender membuat hierarki interaksi membingungkan serta berisiko tertutup sticky CTA. Kelompokkan detail kedatangan setelah tanggal dan beri bottom spacing untuk CTA. | ui-ux |
| 18 | **Idempotency key harus benar-benar disimpan dan diproteksi unique di jalur write yang dipakai app** — membuat key di UI saja tidak cukup; jika hook lokal mengabaikan key, retry dapat membuat order/source ID dan transaksi kedua. Cek sebelum insert, simpan ke kolom `idempotency_key`, dan tangani race `23505` dengan mengembalikan order pertama. | duplicate-order/safety |
| 19 | **App linkbio baru harus punya package, tsconfig, PWA manifest, webroot, dan domain boundary sendiri** — jangan memakai build/deploy target customer/POS; gunakan shared theme secara aman, bundle hanya app baru, dan verifikasi `index.html → hashed assets → domain` setelah deploy. | arsitektur/deployment |
| 20 | **Booking paid tidak otomatis menjadi POS order** — settlement booking tercatat di `financial_transactions.booking_order_id` dengan `order_source_id` kosong, sehingga worker yang hanya mempoll `pos_orders` tidak akan mengirim notifikasi. Booking perlu worker khusus berbasis finance transaction ID, service-role read, dedupe, dan retry setelah Telegram sukses. | notification/booking |
| 20 | **Invoice Mayar harus menerima identitas customer dari sumber order** — nama tidak boleh diganti placeholder jika customer sudah diketahui; email valid customer diteruskan, email kosong memakai default server-side. Validasi ini harus berada di caller dan proxy, serta mapping action create-invoice/get-invoice-detail harus konsisten di shared hook. | payment/integrity |
| 21 | **View booking mengekspos item dengan field `name`, sedangkan consumer POS/Admin mengharapkan `productName`** — normalisasi item di boundary mapper (`productName: item.productName ?? item.name`) sebelum detail, receipt, atau operational list dirender. | debug/data-contract |
| 22 | **Data booking finansial dapat mengirim `null` untuk nominal transfer/total** — kondisi `value !== undefined` masih meloloskan `null`; gunakan `value != null` sebelum render dan `Number(value ?? 0).toLocaleString(...)` untuk mencegah runtime crash. | debug/null-safety |
| 23 | **Tombol checkpoint attendance tidak boleh hanya mengubah state lokal `saved`** — aksi `Simpan` harus memanggil submit flow yang sama dengan checkout utama, membawa checklist/foto ke Edge Function, menampilkan error, dan memakai guard in-flight agar tidak double-submit. | attendance/debug |
| 24 | **Booking operasional membutuhkan state progression yang eksplisit** — setelah `confirmed`, staff perlu checkpoint `arrived` dan `seated` sebelum `completed`; jangan menawarkan tombol langsung selesai karena menghilangkan konteks kedatangan restoran. | booking/ui-ux |
| 25 | **Admin booking perlu memisahkan workspace operasional dan konfigurasi** — kalender/booking/kapasitas harus dipindai sebagai pekerjaan harian, sedangkan halaman publik/menu/formulir perlu preview dan action save terpisah agar tidak membebani scan path staff. | booking/ui-ux |
| 26 | **CTA booking customer harus memakai URL public booking canonical** — placeholder atau string brand seperti `https://Djiwa Tentram/` bukan URL valid dan membuat tombol terlihat tidak bereaksi; verifikasi route lazy bundle dan target public booking dengan HTTP check setelah deploy. | customer/routing/deployment |
| 27 | **Top-up Mayar tidak boleh gagal dengan error generic saat nomor customer kosong** — proxy memakai fallback mobile yang dikonfigurasi, caller wallet meneruskan `error.message` dari proxy, dan UI menampilkan penyebab sebenarnya. | wallet/payment/debug |
| 28 | **Customer contact completeness harus digate sebelum online payment** — home menampilkan notice di bagian atas dengan CTA ke profil, wallet menolak top-up jika email/WhatsApp belum lengkap, dan checkout Mayar/wallet memakai nomor customer (bukan nomor restoran). | customer/payment/ux |
| 29 | **Profile completion setelah login harus modal wajib dan tidak boleh hanya mengandalkan banner** — customer lama dengan data incomplete harus menyelesaikan langkah email/WhatsApp sebelum home penuh atau child route dapat digunakan; payment guard tetap dipertahankan sebagai defense-in-depth. | customer/auth/payment |
| 30 | **Setelah profile save, jangan bergantung hanya pada refresh state async untuk menutup notice** — tandai completion berdasarkan `sourceId` setelah Edge Function sukses, lalu tetap baca ulang database pada login berikutnya; ini mencegah effect membuka kembali banner saat object customer masih stale. | customer/auth/debug |
| 31 | **Order Mayar tidak boleh di-cancel ketika response browser gagal** — invoice provider bisa sudah tercipta atau bahkan paid walau response browser gagal diterima; pertahankan order `pending`, rekonsiliasi status provider server-side, dan izinkan settlement webhook memulihkan order `cancelled` yang terbukti paid. Self-hosted Edge Function harus diperbarui di `/opt/supabase-selfhost/volumes/functions`, bukan hanya Supabase Cloud. | payment/race-condition/deployment |
| 32 | **Klik “Sudah Dibayar” wajib memakai settlement RPC dan memicu refresh progress** — satu transaksi kasir harus atomik (financial transaction + order paid), RPC harus idempotent untuk paid/completed, dan refresh global perlu mencakup `financial_transactions` agar target revenue ikut bertambah segera. | pos/payment/finance |
| 33 | **Progress target harus subscribe ke sumber transaksi, bukan hanya view progress** — setelah settlement, trigger refresh global dengan jeda pendek untuk menunggu commit/recompute view; transaksi harus berstatus `completed` dan order `paid`/`completed` agar masuk revenue target. | pos/finance/realtime |
| 34 | **Filter kategori admin booking tidak boleh memiliki efek samping mengubah featured products** — state filter hanya mengubah hasil tampilan; perubahan katalog harus melalui aksi pilih produk yang eksplisit agar operator tidak mempublikasikan menu tanpa sengaja. | booking/ui-ux/safety |
| 35 | **Calendar booking harus selalu memiliki CTA operasional dan label kapasitas yang eksplisit** — `Tambah Booking` perlu dapat ditemukan langsung dari calendar surface, sementara occupancy harus menyebut `tamu` dan `meja`, bukan singkatan yang memaksa operator menebak. | booking/ui-ux |
| 36 | **Revenue POS target harus memakai definisi gabungan yang eksplisit** — hitung order settled dari `pos` dan `customer_self_service`, kecualikan `pending`/`cancelled` serta income yang ter-link ke booking, gunakan batas hari/shift `Asia/Jakarta`, dan atribusikan tiap shift berdasarkan `orders.created_at` dalam interval shift; settlement terlambat tidak boleh memindahkan order ke shift lain. | pos/finance/debug |
| 37 | **Status layanan customer tidak boleh menganggap data `undefined`/`null` sebagai offline** — `undefined` berarti loading dan `null` berarti query error/unavailable; tampilkan state terpisah agar glitch jaringan tidak menyesatkan pengguna saat top-up sedang diverifikasi. | customer/payment/ux |
| 38 | **Ledger wallet harus membedakan hold dan debit final saat dirender** — `wallet_hold` aktif berarti saldo ditahan, sedangkan `order_debit` berstatus `completed` berarti pembayaran pesanan berhasil; jangan menampilkan note tahap hold sebagai status transaksi final. | wallet/payment/ux |
| 39 | **Deploy Customer wajib memakai webroot canonical `djiwatentram.yumme.id`** — typo path dapat membuat rsync sukses tetapi domain live tetap memakai artifact lama; selalu verifikasi `index.html` dan lazy chunk dari domain setelah copy. | deployment/customer |
| 40 | **Input `type=number` dengan nilai awal 0 harus menyeleksi 0 saat fokus** — jika tidak, ketikan pertama dapat menjadi `01`; pasang behavior global untuk numeric input, tetapi jangan normalisasi input teks seperti WhatsApp, nomor meja, kode menu, atau ID. | ui-ux/input |
| 41 | **Admin customer tidak boleh hanya mempercayai agregat profil lama** — order historical bisa tidak punya `auth_user_id`/email; read model admin perlu fallback matching nama legacy (hapus prefix numerik), hanya hitung `paid`/`completed`, dan tampilkan wallet dari view/ledger. | customer/admin/data-contract |
| 42 | **Reward wallet harus punya tipe ledger dan idempotency key sendiri** — menambahkan trigger reward tanpa memperluas constraint `transaction_type` membuat credit gagal; gunakan reference berbasis order dan verifikasi trigger/RPC setelah migration. | wallet/payment/safety |
| 43 | **Preflight Edge Function self-hosted harus mengembalikan JSON 200** — OPTIONS 204 dapat ditolak gateway; verifikasi HTTP status/body dari endpoint canonical setelah restart container. | edge-function/deployment |
| 44 | **Rename local binding tidak boleh mengubah property response API** — saat `wallet` di-alias menjadi `walletData`, hanya identifier lokal yang boleh berubah; `latest.wallet` tetap mengikuti contract response. | customer/wallet/debug |
| 45 | **Refactor JSX wajib mengaudit import value yang tersisa** — memindahkan komponen wallet dapat menghapus import `Wallet` sementara icon masih dipakai di navigation; build/typecheck route target harus dijalankan setelah ekstraksi. | frontend/refactor |
| 46 | **Screenshot reference harus diikuti secara struktural, bukan hanya secara tema** — untuk home ordering, greeting langsung, summary row, product carousel bergambar, full-width offer banner, dan dua CTA bawah lebih penting daripada sekadar mengganti warna/card radius. | ui-ux/reference |
| 47 | **Better Auth email signup harus membedakan auto-confirm vs email-confirm** — `registrationNeedsEmailConfirm` wajib diisi dari `data.token`; jika tidak, modal menganggap user sudah login lalu kembali ke guest/daftar walau session belum ada. | customer-auth/debug |

| 51 | **Attribution footer harus mengikuti shell content, bukan full-bleed text** — footer booking wajib punya max-width, horizontal alignment, compact hierarchy, readable copy, dan mobile-safe padding; jangan render kalimat panjang langsung sebagai full-width text node. | booking/ui-ux |
