# Lessons Learned

## Frontend

| # | Lesson | Sumber |
|---|--------|--------|
| 1 | **Entry point React wajib me-render root** — TypeScript/Vite dapat tetap typecheck dan build walau file hanya mendefinisikan `App`. Pastikan setiap `main.tsx` memanggil `createRoot(document.getElementById("root")!).render(<App />)` dan verifikasi bundle memuat string UI, bukan hanya React runtime. | debug |
| 2 | **Popup update wajib merender metadata dari version.json** — jangan hardcode commit/message di komponen. Bandingkan semantic version dan commit hash, lalu generate commit subject bersama `version.ts` dan `public/version.json` agar detail release tidak membeku pada pesan lama. | pwa/update/debug |
| 3 | **Receipt export mobile harus dirasterisasi dari dokumen penuh, bukan screenshot viewport** — buat SVG/DOM export dengan ukuran logical tetap, render Canvas pada scale 2–3x, download PNG lossless, dan tunggu asset/font selesai agar file tidak blur atau terpotong. | customer/receipt/ui-ux |
| 4 | **Label Happy Hour harus mengikuti konfigurasi Admin** — gunakan nama promo dan jadwal yang disimpan di Admin sebagai sumber kebenaran. Jadwal canonical saat ini: `08:00–09:00` Sarapan Pagi, `11:00–13:00` Makan Siang, dan konfigurasi malam (POS saat ini `18:00–20:00`) Makan Malam; jangan membuat batas sesi baru di Customer. | customer/promo/ui-ux |
| 5 | **Action receipt harus fixed di atas bottom navigation** — action Split Bill, bukti bayar, dan retry payment tidak boleh menjadi bagian dari alur scroll struk; beri ruang bawah pada konten agar tidak tertutup dan tetap pertahankan CTA retry hanya untuk payment yang belum settled. | customer/receipt/ui-ux |
| 6 | **Asset icon ImageGen wajib diverifikasi alpha channel** — checkerboard pada preview dapat ikut menjadi piksel RGB; cek mode/alpha dan sudut PNG sebelum release, lalu bersihkan background tanpa mengubah silhouette, safe margin, dan palet brand. | customer/assets/ui-ux |
| 7 | **Receipt PNG harus memakai shared brand tokens** — Customer memakai primary biru `#1a5dc6`, surface putih/`#f7f9fc`, dan secondary `#d6e2f5`; jangan mengganti identitas receipt menjadi ivory/coral tanpa bukti dari theme atau logo. | customer/receipt/brand |
| 8 | **Download PNG mobile wajib memakai anchor yang terpasang ke document.body** — `anchor.click()` pada anchor detached dapat diabaikan browser; append sebelum click dan remove setelah revoke object URL agar Bukti Bayar/Split Bill benar-benar memicu download. | customer/receipt/debug |
| 9 | **Nama peserta Split Bill harus menjadi state live** — peserta default seperti `Saya`/`Teman 1` perlu input editable; saat rename, assignment harus dipindahkan ke nama baru dan exporter harus membaca state peserta terbaru agar nama di PNG sama dengan sheet. | customer/receipt/split-bill |
| 10 | **Input editable tidak boleh memakai value yang diketik sebagai React key** — key dinamis menyebabkan input di-remount setiap karakter, fokus hilang, dan keyboard mobile menutup; gunakan key stabil berbasis identitas/index peserta. | customer/mobile/debug |
| 11 | **Ciri khusus customer adalah metadata opsional** — jangan memblokir pendaftaran guest/member atau checkout saat kosong; tetap simpan dan tampilkan nilainya bila customer mengisi, tetapi validasi wajib hanya untuk data yang diperlukan oleh flow pembayaran. | customer/checkout/ux |
| 12 | **Merchandise memakai warna shared Customer** — diferensiasi app cukup melalui layout, komponen, copy, dan flow direct-to-menu; jangan membuat token warna baru yang memecah konsistensi brand. | merchandise/ui-ux/preferensi |
| 13 | **Merchandise catalog-only tidak memerlukan kode menu** — tampilkan katalog sebagai mode tunggal dan hilangkan input nomor, tab kode, keypad, badge nomor, serta scanner dari UI; Customer tetap dapat mempertahankan akses kode bila dibutuhkan. | merchandise/catalog/ui-ux |
| 14 | **Customer SSO lintas brand harus memakai auth server pusat + credentials eksplisit** — kedua storefront mengarah ke Better Auth endpoint yang sama, frontend mengirim cookie dengan `credentials: include`, dan server membatasi `trustedOrigins` ke origin production yang terdaftar; email/password tetap tersedia sementara social login bersifat opsional. | customer-auth/sso/security |
| 15 | **Tombol login lintas app harus memakai return URL allowlist** — Merchandise boleh mengarahkan customer ke halaman auth pusat Djiwa App, tetapi callback hanya boleh kembali ke origin Merchandise yang terdaftar; jangan mempercayai URL redirect arbitrer dari query string. | customer-auth/security/routing |
| 16 | **SSO `returnTo` harus ditandai sebagai handoff** — Customer login/register normal wajib berakhir di `/<slugusername>`; hanya URL auth yang membawa marker `sso=1` boleh kembali ke Merchandise. Tanpa marker, query `returnTo` lama dapat memicu redirect loop lintas storefront. | customer-auth/routing/debug |
| 17 | **Banner promosi customer harus dipasang pada route slug, bukan landing root** — route `/` adalah entry/landing umum; promo customer harus dirender dari home `/<slugcustomer>` agar tidak muncul di halaman publik yang salah. Untuk SPA tanpa route tree, bedakan pathname slug satu segmen dari root dan verifikasi keduanya. | customer/booking/merchandise/routing/ui-ux |
| 18 | **Gambar produk customer wajib punya fallback runtime** — URL gambar katalog/order dapat kosong atau gagal dimuat; pertahankan tinggi area gambar, teks, harga, dan tombol reorder lalu tampilkan ikon produk fallback. Terapkan markup yang sama pada Customer dan Merchandise agar visual tetap sinkron. | customer/merchandise/ui-ux/reliability |
| 19 | **Cross-channel switcher sebaiknya membuka katalog langsung** — jika home Customer dan Merchandise memiliki struktur serupa, link member gunakan `/<username>/order?step=menu` agar perpindahan konteks tidak membuat user melewati home yang sama; guest tetap diarahkan ke `/daftar` karena identitas guest tidak lintas-origin. | customer/merchandise/routing/ui-ux |
| 20 | **Patch shared component wajib memakai konteks signature yang lengkap** — pencarian pendek seperti `}: {` dapat mengenai komponen lain dalam file yang sama; gunakan blok fungsi + nama komponen sebagai konteks dan jalankan build segera setelah perubahan props. | frontend/debug |
| 21 | **Storefront B2B tanpa meja harus menghapus meja di seluruh flow** — jangan hanya menyembunyikan field pendaftaran; hilangkan juga state URL, input checkout, metadata payload, banner menu, dan struk. Gunakan `orderType: takeaway` agar order tidak diklasifikasikan sebagai dine-in. | b2b/checkout/debug |
| 22 | **CTA produk spesifik harus mempertahankan intent melewati form guest** — simpan marker non-PII di origin sendiri sebelum `/daftar`, konsumsi sekali setelah validasi, lalu arahkan langsung ke katalog/order; jangan meneruskan PII lewat query lintas domain. | b2b/routing/ui-ux |

## Supabase

| # | Lesson | Sumber |
|---|--------|--------|
| 1 | **Gunakan nama kolom schema aktual saat membaca tax policy** — `pos.tax_policies` memakai `effective_until`, bukan `effective_to`; validasi kolom melalui `information_schema` sebelum query/update. | debug |
| 2 | **Bedakan cloud project dan custom self-hosted URL** — `supabase db query --linked` menargetkan project cloud, sedangkan aplikasi memakai `supabase.yumme.id`. Selalu smoke-test kedua endpoint dan apply migration/deploy function ke runtime yang benar. | deployment |
| 3 | **Extension PostgreSQL dapat berada di schema `extensions`** — gunakan `extensions.digest(...)`, bukan `digest(...)`, pada function SECURITY DEFINER agar tidak bergantung pada `search_path`. | debug |
| 4 | **Payment booking harus payment-first** — simpan booking sebagai `pending` dengan hold kapasitas singkat, buat invoice Mayar lewat Edge Function, korelasikan `extraData.bookingId`, dan ubah menjadi `confirmed/paid` hanya setelah webhook memverifikasi `GET /transactions/{id}` berstatus `paid`. Redirect browser bukan bukti settlement. | payment |
| 5 | **Booking yang sudah terhubung ke finance tidak boleh di-hard-delete** — aksi hapus harus mengecek `financial_transactions`; jika ada linkage, ubah booking menjadi `cancelled` dan simpan `cancelled_at`. Physical delete hanya boleh untuk booking tanpa transaksi finansial. | safety |
| 6 | **Mini App closing wajib diverifikasi ulang di server** — jangan hanya percaya state frontend atau link verifier; `process-closing` harus memvalidasi HMAC UID/timestamp, active check-in, dan menolak duplicate checkout sebelum opname/inventory write. Settings jadwal yang gagal dibaca tidak boleh menjadi bypass validasi jam. | security |
| 7 | **Build sukses tidak berarti production sudah berubah** — untuk SPA/PWA, verifikasi `index.html`, hashed bundle, `sw.js`, dan `version.json` dari domain canonical setelah deploy. HTTP 200 pada route dapat tetap menyajikan build lama. | deployment |
| 8 | **Self-host PostgreSQL tidak selalu menyediakan helper JSONB yang diasumsikan** — RPC harus diuji pada engine production; gunakan operasi JSONB portable seperti `v_updates <> '{}'::jsonb` dan transactional rollback test sebelum rollout. | debug |
| 9 | **Setiap app Vite wajib punya publishable Supabase key saat build** — fallback URL saja tidak cukup; `import.meta.env` dibekukan saat build sehingga app tanpa `VITE_SUPABASE_PUBLISHABLE_KEY` masuk state “Supabase belum dikonfigurasi”. Simpan key production di env ignored dan sediakan `.env.example`. | deployment |

|| 9 | **Setiap app Vite harus membawa env build sendiri** — cloning app tidak otomatis menyalin file `.env` yang di-ignore Git; tanpa `VITE_SUPABASE_PUBLISHABLE_KEY`, Vite membekukan konfigurasi kosong ke bundle dan runtime menampilkan “Supabase client key is not configured”. Sediakan `.env.example`, salin env production secara aman sebelum build, dan verifikasi marker bundle + REST 200. | merchandise/deployment/debug |
|| 10 | **Clone app wajib menyiapkan env publishable sebelum build pertama** — `.env` sengaja tidak masuk Git, sehingga app baru dapat ter-build tetapi Supabase client tetap tidak terkonfigurasi. Salin hanya variabel `VITE_*` dari app sumber, jangan membawa service secret, lalu rebuild sebelum deploy. | b2b/deployment/debug |
