## 1. 🔴 `registration_counters` — Enable RLS + Tambah Policies

### Masalah
- Tabel dibuat di `20260521000001_create_registration_counters.sql`
- ✅ RPC `next_registration_number()` sudah `security definer` → bypass RLS → **aman**
- ❌ Tabel **tidak** di-enable RLS → anon bisa akses langsung via REST API
- Risiko: siapapun dengan anon key bisa reset counter, insert kategori palsu, baca semua counter

### Solusi

**File:** Migration baru `20260521000008_enable_rls_registration_counters.sql`

```sql
-- =============================================================================
-- Fix: Enable RLS + add policies untuk registration_counters
-- 
-- Masalah: Tabel tidak punya RLS sama sekali. Anon bisa reset/insert/read counter
-- langsung via REST API, bypassing RPC next_registration_number().
-- 
-- RPC next_registration_number() sudah security definer → tetap bisa INSERT/UPDATE
-- meskipun RLS di-enable.
-- =============================================================================

alter table public.registration_counters enable row level security;

-- SELECT: anon bisa lihat counter (dibutuhkan frontend untuk display)
drop policy if exists "anon_select_registration_counters" on public.registration_counters;
create policy "anon_select_registration_counters"
  on public.registration_counters for select to anon, authenticated
  using (true);

-- INSERT/UPDATE: hanya via RPC (security definer) atau edge function
-- Tidak ada alasan frontend langsung nulis ke tabel ini
-- NOTE: RPC next_registration_number() adalah security definer → bypass RLS → tetap works
```

**Pertimbangan:**
- RPC `next_registration_number()` adalah `security definer` → akan terus bekerja setelah RLS di-enable
- Tidak perlu INSERT/UPDATE policy untuk anon → semua write harus via RPC
- Jika ada kebutuhan admin write langsung, bisa ditambah nanti

## 2. 🟠 `contract_approvals` — Fix RLS untuk Better Auth

### Masalah
- Semua 3 policy (SELECT/INSERT/UPDATE) menggunakan `auth.role() = 'authenticated'`
- Karena Better Auth, `auth.role()` selalu `'anon'` → policy **tidak pernah match**
- Efek: tidak ada yang bisa baca/tulis `contract_approvals` dari frontend
- ✅ Frontend **tidak** ada yang import `contract_approvals` → mungkin hanya akses via edge function → **dead policy**

### Opsi A: Ubah ke anon (sederhana, seperti employee_onboarding)
```sql
drop policy "Contract approvals are readable by authenticated users"
  on public.contract_approvals;
drop policy "Contract approvals can be inserted by authenticated users"
  on public.contract_approvals;
drop policy "Contract approvals can be updated by authenticated users"
  on public.contract_approvals;

create policy "contract_approvals_anon_select"
  on public.contract_approvals for select to anon, authenticated
  using (true);

create policy "contract_approvals_anon_insert"
  on public.contract_approvals for insert to anon, authenticated
  with check (true);

create policy "contract_approvals_anon_update"
  on public.contract_approvals for update to anon, authenticated
  using (true) with check (true);
```

### Opsi B: Via Edge Function (lebih aman) — rekomendasi
> Karena sudah ada pattern `onboarding-admin` edge function, lebih baik extend function itu untuk contract approvals juga.

**Yang perlu diubah:**
1. `supabase/functions/onboarding-admin/index.ts` — tambah action `approve_contract`, `reject_contract`, `sign_contract`
2. RLS policies contract_approvals — biarkan untuk service_role (edge function bypass via service_role key)

### Rekomendasi: **Opsi A** dulu (yang penting berfungsi), upgrade ke Opsi B nanti jika perlu.

## 3. 🟡 Payroll Tables — Konfirmasi + Fix

### Masalah
7 payroll tables di `pos` schema:
- `payroll_periods`, `payroll_runs`, `payroll_run_items`, `payslips`, `payroll_audit_logs`, `payroll_role_rules`, `payroll_user_overrides`

Semua punya pola yang sama:
| Policy | Roles | Cmd |
|--------|-------|-----|
| `Authenticated read access on ...` | `{authenticated}` | SELECT |
| `Service role full access on ...` | `{service_role}` | ALL |

Pertanyaan: **Apakah payroll tables diakses langsung dari frontend? Atau hanya via edge function/RPC?**

**Jika via edge function** → ✅ **Tidak masalah.** Service_role key bypass RLS.

**Jika ada akses langsung frontend** → perlu ditambah `anon` policies.

### Verifikasi yang perlu dilakukan
- Search frontend untuk query payroll tables
- Check apakah ada public views untuk payroll yang terpengaruh
- Confirm dengan user

### Fix jika diperlukan
```sql

drop policy if exists "payroll_periods_anon_select" on pos.payroll_periods;
create policy "payroll_periods_anon_select"
  on pos.payroll_periods for select to anon, authenticated
  using (true);

-- ... (ulang untuk setiap payroll table)
```
