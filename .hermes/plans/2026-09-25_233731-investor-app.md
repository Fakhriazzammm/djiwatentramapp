# Djiwa Tentram Investor App Implementation Plan

> **For Hermes:** Implement task-by-task using the repository's feature workflow; do not deploy or expose production data until the access and disclosure gates below pass.

**Goal:** Build a standalone, responsive `apps/investor` for individual/private investors, with an evidence-led public investment overview, controlled investor data room, live business metrics sourced from the VPS database, and an investor-interest/expansion pipeline.

**Architecture:** Add a separate React/Vite/TanStack Router app in the existing monorepo, reusing established workspace packages and design tokens. Keep public content separate from financial disclosure: public routes consume purpose-built aggregate endpoints/views; detailed financials and source documents require verified investor access. Use the existing VPS-hosted Supabase as the authoritative source, and add only additive, least-privilege database/API surfaces after auditing current schema, RLS, auth, and finance semantics.

**Tech Stack:** Existing React 19, Vite, TypeScript, TanStack Router, Tailwind v4, Better Auth React client, Lucide, Sonner, shared workspace packages. Investor database reads go through the existing Hono/Better Auth service; the browser has no direct finance-table client.

## Architecture and Data-Disclosure Decision

### Recommended: dedicated aggregation/API boundary

1. Browser reads only public approved aggregate data from dedicated read-only DB views/RPCs or a server-side endpoint secured for public-safe aggregates.
2. Detailed private datasets are read only through an authenticated/authorized server-side boundary or narrowly scoped DB policies, with investor identity and permission checks. Never place `service_role` credentials in Vite environment variables.
3. Reuse the current Supabase/VPS and auth architecture only after discovery of its exact supported investor auth/session flow. Do not assume employee or customer auth is an appropriate investor identity model.
4. Realtime subscription is limited to safe aggregate invalidation/update signals; if underlying tables cannot safely be subscribed to, poll the aggregate endpoint at a modest cadence and show freshness. Do not subscribe publicly to raw finance tables.
5. Make all new DB objects additive and idempotent; preserve historical finance rows. Any schema change requires explicit migration review, backup/rollback, grants/RLS tests, and production release coordination.

### Endpoint / REST mapping (implemented MVP + planned expansion)

- Investor auth: Better Auth handler `/api/investor-auth/*` (Google only).
- Access status: `GET /api/investor/access` — requires investor auth session; returns `approved`, `pending`, `suspended`, or `none`.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Existing finance view broadly grants anon/authenticated access | Do not use it directly; narrowly aggregate in a reviewed API/view/RPC, test grants/RLS and payloads |
| Finance source semantics differ across orders, transactions and accounting | Reconcile with current Admin Finance, document metric formula and regression fixtures before display |
| Investor expects “all numbers” to be public | Separate public approved aggregates from all detailed disclosures in a verified data room; explicitly approve disclosure tier |
| Private investment solicitation has legal requirements | No offer/guaranteed-return language; get qualified legal/finance review before publication |
| PII in investor lead forms | Minimize fields, consent, rate limiting, least privilege, retention/deletion policy, no PII in logs/Telegram |
| Investor authentication differs from employee/customer auth | Discover a supported separate identity/session model; fail closed, no accidental access via employee role |
| Realtime leaks raw row events or overloads DB | Subscribe only to safe aggregate snapshots or use bounded polling with freshness state |
| New app changes shared monorepo/deploy state | Isolated app package and deploy target; do not change shared design tokens/production app routing without need |
| Investment forecasts appear as promises | Label assumptions/projections, show scenario and methodology, legal review; use only approved stored inputs |
| New DNS record or vhost affects existing service | Inspect Hostinger zone and VPS routing; additive record and dedicated vhost; staging, regression checks, rollback recipe |
